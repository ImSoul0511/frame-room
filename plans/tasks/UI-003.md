# UI-003: Role-aware frontend workflow demo

Status: In Review

## Request and authority

The user requested a careful reread of `D:\rup_ucspec-v2.docx`, role-appropriate
navigation and the missing features as a frontend-only mock demo. The Word file is
a requirements reference, not permission to modify backend services, database data,
policies or credentials. The current request supersedes live implementation of the
new business interactions. Earlier authorized authentication and public catalog

The previously removed standalone sample-profile feature and its routes remain
removed. There is no AI-usage panel. Existing cream, lavender and blue styling,
Vietnamese-capable typography, horizontal header navigation and separate username
search are retained.

## Navigation and permissions

| Viewer         | Primary header navigation                               | Scope                                                                 |
| -------------- | ------------------------------------------------------- | --------------------------------------------------------------------- |
| Visitor        | Explore                                                 | Public discovery, filtering, profiles and portfolios                  |
| Client         | Explore, Projects, Bookings, Messages                   | Own ideas, booking requests, agreements, photo selection and reviews  |
| Photographer   | Bookings, Messages, Profile & work, My studios, Explore | Personal work/packages and currently assigned studio bookings         |
| Studio manager | Same professional navigation                            | Manager tabs only in studios where this person has manager membership |
| Administrator  | Moderation, Explore                                     | Report decisions, review reassessment and manual dispute holds        |

Account/profile editing and notifications are accessible through the header.
A person can be a manager in Frame Studio and an ordinary photographer in Light
Studio. Display specialties never grant management privileges. Assigned studio
photographers cannot read general client-studio messages or other bookings'
messages. Route guards, displayed actions and the local state reducer use the
same role/membership rules.

The explicit **Demo session / View as** controls are for previewing these actors.
They do not create accounts, change Supabase claims or authorize live operations.
The default Account role is derived from the existing verified account profile.
Demo state is shared across role switches and cleared by reload or Reset demo.

## Follow-up: hot-update context and Auth client lifetime

The user reported `DemoProvider is required` in AppLayout and Supabase's multiple
GoTrueClient warning after the development updates. Source inspection confirms
that App wraps its routes in DemoProvider and that only one browser createClient
call site exists. The symptoms are consistent with module re-evaluation during
hot updates: a new context identity can disagree with a retained provider, and
re-running the API module creates another Auth client for the same storage key.
This was not reproduced in an attached browser.

DemoContext, AuthContext and the Supabase client now retain their identity in
their own module's `import.meta.hot.data`. Production still initializes each
resource normally. This uses Vite's documented [persistent hot data](https://vite.dev/guide/api-hmr#hot-data).
No error is suppressed and the missing-provider guard remains active. Backend,
database and environment configuration are unchanged. After applying this change,
the already-open page needs one full reload to discard instances created before
the cache existed. Environment changes still require the existing server restart
and page reload workflow.

Regression coverage renders an updated consumer beneath the previous context
provider, verifies one Auth factory invocation, handles a null/unconfigured client,
and isolates fresh page/production initialization. All 53 frontend tests passed;
web TypeScript, changed-file ESLint and production build passed. The existing
bundle-size warning remains. Browser-extension messaging (`runtime.lastError`)
has no identified application call site and was not diagnosed as this crash.
