# UC-001 — RUP use-case coverage and implementation plan

Status: In Review. Supabase Cloud acceptance is pending.

## Scope and baseline

This audit covers version 1.3 of the [RUP specification](../../rup_ucspec-v2.docx.md) against the local `dev` working tree at `ab458d2`, including uncommitted work. UC9 is excluded because its main flow requires AI Search. Public provider pages remain entry points for booking, contact, and reporting. The plan assumes real accounts and persisted, multi-user data are the acceptance baseline.

The [router](../../apps/web/src/App.tsx) mounts demo components for key account, studio, catalog, booking, messaging, and admin routes. [DemoContext](../../apps/web/src/features/demo/DemoContext.tsx) stores mutations in React state even when the displayed role comes from a real account. The API-backed booking workspace is reachable under `/bookings/live`. Several other API-backed pages exist in source and can be reused when wiring real navigation.

## Work and acceptance by UC

### Accounts and provider catalog

**UC11 — Log in**

- Use Supabase session and server-derived permissions for real navigation. Prefer an explicit safe return URL, with a role-appropriate destination as the default. Connect protected routes to real auth guards before exposing them in account navigation.
- Accept when Client, Photographer, Studio Manager and Admin reach their permitted locations, an authorized return URL survives login, and invalid credentials return a generic error. Verify expired sessions and cross-Studio access with real accounts.

**UC13 — Register account**

- Keep the explicit onboarding flow and use the verified Auth ID for profile creation and retries. Make Client and Photographer provisioning resumable after email confirmation or a partial write. Show registration success when the selected application profile is ready.
- Accept when both roles can register, invalid or duplicate submissions do not create extra accounts, and a simulated failure between profile writes recovers with the same Auth ID and role choice.

**UC7 — Set up Photographer profile**

- Connect real profile and settings routes to the existing Photographer create/read/update APIs. Complete field validation for contact information, biography, location, professional roles, genres and styles. Keep professional labels separate from permission grants.
- Accept when setup and edits survive reload, duplicate setup routes to the existing profile, unauthorized edits fail, and the completed profile enables personal portfolio and package management.

**UC4 — Create Studio**

- Mount the API-backed Studio flow in account mode. Complete location/contact fields where needed. Keep Studio creation and manager membership in one transaction and route to the new Studio dashboard.
- Accept when an eligible Photographer can create a Studio and immediately manage it from a separate session. Invalid or abandoned submissions leave no Studio or membership.

**UC5 — Manage Studio members**

- Connect the existing team, invitation and role APIs to the live dashboard. Provide eligible Photographer search, pending invitations, accept/decline actions, manager/member controls, and auditable notifications. Build the active-assignment guard response with an authorized list of affected bookings for the UC16 handoff.
- Accept when invitation and role changes persist across accounts, duplicate invitations are blocked, removing an actively assigned member identifies the affected bookings, and removal works after eligible reassignments. Preserve historical contributions and verify access removal.

**UC6 — Upload Photographer/Studio portfolio**

- Reuse the live portfolio editor and media processing. Support staging images with provenance, style tags and optional crew credits. Validate required metadata and at least one valid image at publish time. Verify the same authorization on personal and Studio operations.
- Accept when a published portfolio appears on the public provider page with its image metadata, an invalid upload remains repairable in draft, and draft content and unauthorized Studio writes are blocked.

**UC8 — Manage service packages**

- Use the existing personal and Studio package APIs/forms for publish, edit and unpublish. Add explicit photo selection quota and revision limits to the shared package contract. Include them in the booking snapshot so later package edits preserve agreed terms.
- Accept when public pages show the correct published packages, invalid terms and unauthorized edits fail, and editing or unpublishing a package preserves earlier booking terms.

### Contact and booking

**UC17 — Chat with Photographer or Studio**

- Add a persistent Conversation keyed by Client and exact provider identity, with messages carrying sender, server time, optional Booking ID and submission ID. Use a race-safe find-or-create operation. Validate that a supplied booking belongs to the same pair. Authorize list, read, send, attachment download and Realtime visibility.
- Connect public Contact and the live inbox. Support login return, provider replies, attachments up to 50 MB, timeline pagination, and retry with the original submission ID. Distinguish persistence failure from delayed Realtime delivery. Migrate legacy room messages into the correct booking scope while preserving IDs, timestamps, senders and file references where supported.
- Accept when parallel Contact attempts and repeat contact return the same thread, multiple bookings share it, a browser reconnect or send retry creates one message, and an assigned Studio Photographer sees only the messages and files for authorized bookings.

**UC10 — Assign Photographer to Studio Booking**

- Add a dedicated pending assignment action for Studio Managers. Reuse the reservation and eligibility rules to show availability and validate current membership, schedule and booking version. Record the selected Photographer, manager, timestamp and validation outcome. Send the assignment notification after commit.
- Accept when valid assignment leaves the booking pending with no Shoot Room access, an unavailable or ineligible candidate is rejected, and UC1 rechecks eligibility and conflicts at confirmation.

**UC1 — Create Shoot Brief and book**

- Connect the public service CTA to a live form with package details, schedule, reference images and logistics. In one transaction create the pending Booking and Brief v1, record the Client approval, freeze package terms and link any existing Conversation. Provide a remediation path for existing pending bookings without a brief.
- Add revision, rejection and pending cancellation actions. Confirm only when the latest BriefVersion has both approvals and the schedule and Studio assignment are valid. Make reservation, confirmation, agreed-version update and Shoot Room provisioning atomic. Persist notifications and approval/transition history.
- Accept when solo and Studio flows complete through the normal public CTA, a later brief invalidates stale approval for confirmation, and conflicting concurrent confirmations cannot create extra rooms or reservations. Verify rejection, pending cancellation and invalid form submission.

### Shoot Room and delivery

**UC2 — Collaborate in Shoot Room**

- Show the booking-scoped portion of UC17 with the agreed brief, references and milestones. Enforce `confirmed` and `in_progress` collaboration state for API actions and Realtime visibility. Keep proofing and delivery available through their own authorized booking views.
- Persist immutable brief proposals, counterparty decisions, changes to the agreed version, and milestone actor/time. Implement cancellation proposal, acceptance and decline, with the transition and audit written only after both sides agree. Share the cancellation workflow with UC3.
- Accept when two sessions receive eligible message, attachment and milestone updates at p95 within one second in the test environment, an outsider cannot subscribe or fetch a file, and scope/cancellation changes take effect only after counterparty approval. Starting service requires its own provider action.

**UC16 — Reassign Photographer to Studio Booking**

- Add a dedicated action for replacement on an eligible active Studio booking. Validate booking version, current assignee, manager permissions, replacement membership and scheduling together. Atomically swap reservations and assignee, then persist old/new IDs, actor, server time and reason. Notify the Client and both Photographers.
- Route assignee changes through the dedicated action. Recheck current access on message and attachment reads, including following a previously obtained reference after reassignment. Keep general Client–Studio history restricted. Link the UC5 affected-booking view to this action.
- Accept when reassignment keeps the existing brief, room, history and status, an unavailable replacement leaves assignment intact, and concurrent removal/reassignment respects both membership and booking rules. Test former access revocation, new access, and access retained through an independent authorized role.

**UC3 — Proof, annotate and approve photos**

- Publish optimized protected previews and persist coordinate pins and per-image notes by selection round. Enforce the agreed quota, explicit reopen requests and revision limits server-side. Resolve legacy snapshot terms before enforcement. Require a submitted selection before accepting final uploads and at least one valid final file before delivery.
- Wire mutual cancellation during proofing and keep delivery download authorization short-lived. Apply and verify the existing 168-hour completion migration and worker, plus administrator hold and resume based on remaining time. Record automatic and manual completion as distinct audit events.
- Accept when normalized pins remain aligned on mobile and desktop, quota/revision boundaries hold under concurrent requests, and Client files become downloadable at delivery. Cover manual completion, expiry, hold/resume and racing completion actions with one final transition. Both completion paths enable one review.

### Reporting and reviews

**UC15 — Report content or review**

- Wire authenticated reporting from public Portfolio, Portfolio Image and Review surfaces to the existing API. Validate allowed reasons and resolve target visibility at submission time. Persist reporter, target, reason, optional details, timestamp and pending state.
- Accept when the report appears in a separate Admin session, private or removed targets are rejected, and form input survives validation failure.

**UC14 — Moderate reported content and reviews**

- Deliver the live queue and detail view with authorized target context, evidence and history. Model pending, actioned and dismissed outcomes with required decision reasons. Update report status, visibility and audit atomically. Preserve legacy report data where the previous outcome is ambiguous.
- Add a reassessment queue for UC12 and audit approval and rejection. Enforce visibility consistently in public API reads, rating summaries and public media delivery.
- Accept when an admin can hide, dismiss or defer a report with a timestamped audit entry, non-admin access fails, and review reassessment changes public visibility and rating counts correctly across sessions.

**UC12 — Review Photographer or Studio**

- Finish the live review form and server validation for a completed booking, its Client and the existing unique review constraint. For Studio bookings, associate the review with the assigned Photographer and Studio at completion. Show the hide reason to the author and save revisions against the same Review ID, with an audit and hidden status pending UC14 reassessment.
- Accept when manual and automatic completion each unlock one review, a second submission or out-of-range value is rejected, and an edited hidden review affects public ratings only after admin approval.

## Implementation

- The account routes now use Supabase Auth and the persistent API. The explicit
  role selector opens the demo. Account registration resumes incomplete
  Photographer provisioning with the same Auth ID.
- The booking request transaction creates Brief v1 and records Client approval.
  It links an existing Conversation and reuses a successful request after a
  retry. Studio assignment, confirmation, reassignment, agreement changes and
  mutual cancellation use separate operations with current state checks.
- General and booking-scoped messages share a persistent timeline with scoped
  Realtime and authenticated Storage reads. The migration backfills legacy room
  history while preserving identifiers and paths.
- Proofing persists round-specific notes and pins, enforces selection limits,
  and accepts delivery files for a submitted round. Legacy booking snapshots
  use a quota derived from the frozen retouched count, with a default of five
  when the count is unavailable, and two revision rounds.
- Studios, membership, packages, portfolio uploads, content reports, and
  review reassessment write through the API. Legacy resolved reports retain
  their known state without a reconstructed outcome. Portfolio media uses
  current publication and moderation rules for managed Storage objects.
