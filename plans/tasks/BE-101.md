## Goal and implemented scope

The historical target was 2026-11-12. Both stages are implemented in this branch:

1. Validated environment, stable error envelope, Supabase bearer verification,
   transaction-scoped database adapter, module/route interface and OpenAPI registration.
2. Six identity routes: `GET/POST/PATCH /v1/me` and
   `GET/POST/PATCH /v1/photographers/me`.

System routes are `GET /health`, `GET /v1/config` and `GET /v1/openapi.json`.
Health remains unenveloped; business success responses use `{data: ...}`.

Out of scope: catalog, uploads, search, booking, AI, migrations, generated DB types,
`Accept-Language` and `Idempotency-Key` handling.

## Dependencies and decisions

- This PR already includes the MVP `business.ts` and `locale.ts` shared schemas.
  The earlier statement that stage 2 had not started was stale.
- The caller's own photographer response schema now lives in
  `packages/shared/src/business.ts`; the API keeps a compatibility re-export.
  Khoa must review compatibility with the separate frontend/shared handoff.
- Implemented behavior preserves the MVP: read-only `GET /v1/me` returns
  404 `profile_required` when absent; `POST /v1/me` returns 201 on creation and
  200 with the existing profile on same-user retry.
  [ADR 0003](../../docs/adr/0003-auth-profile-initialization.md) remains Proposed.
  Ly, Khai and Khoa still need to record the accepted initialization decision.
- Unknown object keys are stripped using Zod defaults, following Khai's 2026-11-13
  decision. Identity and roles never come from those keys.
- Current unavailable-dependency mapping is 503. The future model-error mapping
  decision belongs to AI integration.
- Dependencies are `pg`, `@types/pg`, `@supabase/supabase-js` and
  `zod-to-json-schema`; coordinate subsequent lockfile changes.
- Cloud verification needs DB-101/DB-102 and a designated test environment.
  On 2026-11-17 the user explicitly deferred Supabase Cloud verification.
